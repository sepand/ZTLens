# ZTLens

Mapping Zero Trust capabilities across DoD, NIST, and compliance frameworks — one lens, many standards.

An independent, community-oriented reference for understanding and implementing Zero Trust (ZT) architecture — built around the **DoD Zero Trust Reference Architecture (RA) 2.0** and **NIST SP 800-207**, cross-walked to widely used regulatory and industry frameworks.

This repo exists to make Zero Trust concepts approachable: what the pillars mean, what "maturity" looks like in practice, and how ZT capabilities map to the compliance frameworks most teams actually have to satisfy (NIST 800-53, PCI-DSS, GLBA, NYDFS 500, SOX, etc.).

> **Disclaimer:** This is an independent educational interpretation of publicly available Zero Trust guidance. It is **not** an official DoD, NIST, CISA, or any other agency/vendor publication, and is not affiliated with or endorsed by any employer of the maintainer. Always consult primary sources (linked below) for authoritative requirements.

### Vendor data

The [Zero Trust Matrix](https://sepand.github.io/ZTLens/zero-trust-matrix) page has a Vendors toggle showing vendors identified in each pillar's marketplace category. `data/vendors.yaml` is auto-generated by [`.github/workflows/sync-vendors.yml`](.github/workflows/sync-vendors.yml), which runs on the 1st and 15th of each month (or on demand) and pulls from three sources:

- **AWS Marketplace Discovery API** — live, self-serve. Create an IAM user with **only** the custom policy at [`scripts/vendor-sync/aws-iam-policy.json`](scripts/vendor-sync/aws-iam-policy.json) attached (`aws-marketplace:SearchFacets` + `aws-marketplace:SearchListings` — the two calls the script actually makes; narrower than AWS's own `AWSMarketplaceDiscoveryFullAccess` managed policy, which also grants several `Get*`/`List*` actions this script never uses). Generate an access key for that user and add it as the `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` repo secrets — GitHub encrypts secrets at rest and they're never exposed in logs or to forks/PRs from outside collaborators. (OIDC role assumption would avoid even a long-lived key, but static least-privilege credentials scoped to a read-only, non-resource-owning action pair are a reasonable, simpler tradeoff here.)
- **Azure Marketplace Catalog API** — live, but requires an API key requested by email from Microsoft's Marketplace Catalog team (not self-serve). Add it as the `AZURE_MARKETPLACE_API_KEY` repo secret once obtained; skipped gracefully if unset.
- **Google Cloud Marketplace** — has no public catalog-search API (its Consumer/Partner Procurement APIs only cover orders and entitlements, verified directly against Google's REST resource tree), so GCP vendors come from a hand-curated seed list at [`scripts/vendor-sync/manual-vendors.yaml`](scripts/vendor-sync/manual-vendors.yaml) instead. That file is merged into every sync run and untouched by the automated fetch — edit it directly to add/update GCP entries, and revisit periodically since it isn't verified live the way AWS/Azure entries are.

Vendor presence is informational only — it's not a certification, partnership, or endorsement (see the disclaimer shown on the page). Edit [`scripts/vendor-sync/pillar-keywords.yaml`](scripts/vendor-sync/pillar-keywords.yaml) to change which marketplace categories map to which pillar.

## Why Zero Trust

Traditional network security assumes that anything inside the perimeter can be trusted. Zero Trust starts from the opposite assumption: **no user, device, or workload is trusted by default — regardless of location** — and every access request must be explicitly verified, authorized, and continuously evaluated.

Two foundational references anchor this repo:

- **[DoD Zero Trust Reference Architecture 2.0](https://dodcio.defense.gov/Portals/0/Documents/Library/(U)ZT_RA_v2.0(U)_Sep22.pdf)** — defines 7 pillars and a capability-based maturity model (Traditional → Advanced → Optimal).
- **[NIST SP 800-207: Zero Trust Architecture](https://nvlpubs.nist.gov/nistpubs/specialpublications/nist.sp.800-207.pdf)** — defines the tenets, logical components, and deployment models of ZTA.

## Maturity model

Every capability in the matrix is scored across three stages, per DoD ZT RA 2.0:

1. **Traditional** — largely manual, perimeter-based, siloed controls
2. **Advanced** — automated policy enforcement within pillars, some cross-pillar signal sharing
3. **Optimal** — fully automated, dynamic, risk-based enforcement with continuous cross-pillar telemetry

See [`/capability-matrix`](capability-matrix/) for the full table.
